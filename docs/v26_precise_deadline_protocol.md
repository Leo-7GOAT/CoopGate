# 统一超时计时的配对验证协议

已完成的84次进程隔离实验暴露出内部`monotonic`与外部`perf_counter`的计时精度差异。本机研究Python中前者分辨率为15.625 ms，后者为0.0001 ms。450 ms预算曾对应约441.987—475.711 ms的实测超时回调。旧实现、原始结果与限制原样保留。

新增`PreciseDeadlineProfile`沿用原实现的进程隔离、输入验证、物理检查、初始准入标签、首次故障后持续回退及显式清理。控制选择函数只将八处时钟读取改为`perf_counter`，由AST比较验证；准备时间也用同一高分辨率时钟计量。改变计时可能改变恰好靠近截止时刻的选择，因此不能仅凭代码差异很小就宣称整个闭环等价。

## 完整配对范围

- 原有全部84种案例：同一个旧初态、3份固定模型、4种扰动、7种分支。
- 每种案例重新运行原计时和高分辨率计时，共168次实际SUMO执行。相邻成对，交替先后顺序。
- 七种分支保留直接基线、初始拒绝、正常学习、第4步延迟2秒、永久卡住、异常、NaN。内部预算仍为450 ms，决策周期仍为500 ms。
- 使用原有故障注入器与独立轨迹复核程序。所有实际采用的主策略命令和基线命令均重新计算验证；每种实现的拒绝轨迹与直接基线比较。
- 保存所有行和逐步字段，只有预先列出的计时/进程标识字段不参与行为等价判断。近截止时刻产生的不同选择保留并报告，不能删掉或重跑。
- 报告全部回调耗时、最大值、超过450/500 ms计数、超时触发相对预算的偏差，以及启动和清理成本。只在执行会话实际返回成功退出后汇总。

这是在两项正式实验并行运行期间完成的工程验证。它不增加独立有效性初态，不使用进行中的风险校准结果，不修改正式研究的控制器。学习分支人为设为可用，用于触发故障，不能用来证明置信度门控的筛选能力。

## 保证的边界

统一时钟消除同一预算计算中计时来源不一致的问题，但不能控制操作系统调度、基线计算或主线程复核耗时。完整回调仍可能超过预算。SUMO在回调返回后才推进物理时间，本实验没有模拟等待期间车辆继续运动，也不测量网络通信延迟。

旧控制器的统计认证不能自动转给修改后的控制器。若超时改变实际采用事件和访问状态，采用后的退化风险也会改变。接入正式门控前需要针对固定的完整实现及运行负载重新验证，而不能借用原实现的证书。

## 运行入口

`python tools/audit_precise_deadline_v26.py freeze`要求源文件已经提交；冻结协议提交后才能`run`。保存真实执行退出凭据后，`summarize`校验完整案例、结果和复核清单，再生成全部配对差异及耗时表。
