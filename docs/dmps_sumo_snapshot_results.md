# 原版 DMPS 的 SUMO 分支接口验证结果

使用提交 b20e2678 的独立原生进程恢复实现，八个固定开发前缀全部完成，工具会话
9025 返回退出码 0。对应源代码、运行环境、全部保存记录及独立物理重算已核验。
这不是八个完整性能评估回合：每个前缀固定 12 步，共 96 个实际决策、480 个实际
物理子步，只包含两个初态跨四类动力学复用。

| 动力学 | 前缀 | 实际决策 | 原 MCTS 干预 | 路由几何违反 / 碰撞前缀 |
|---|---:|---:|---:|---:|
| nominal | 2 | 24 | 14 | 0 / 0 |
| gain_drag | 2 | 24 | 14 | 0 / 0 |
| lag_mild | 2 | 24 | 14 | 0 / 0 |
| lag_strong | 2 | 24 | 12 | 0 / 0 |

全部检查包含两级嵌套保存/恢复、相同动作分支重放、采样 RNG 恢复和每次原
check_action 后的主环境恢复。原 MCTS 在每次真实 take_step 后只留下一个实际控制
步，主环境的扰动游标、执行器记忆、回合轨迹与原生时钟一致。固定输入中观察到
54 次实际干预，因此不是只走原提案直接通过路径的空验证。

总计发生 1,314 次快照载入和 6,002 个仿真决策调用，后者包括接口检查及预测，不能
当作真实执行步数或独立样本。每次载入重启本环境拥有的 SUMO 进程，成本很高；
该实现是正确性参照，不是实时部署方案。原作者 mcts.py 函数体未修改，critic
恒为零，本轮训练步数为零。

## 保留的失败与实际修正

首版在 128 位 RNG 状态比较上发生类型错误。修正比较器后，快速加载初始快照发生
原生车辆不移动的重放偏差；完整加载又暴露原生子步时钟与 Python 计数不一致；
显式子步目标仍不能可靠回载初始状态。改用独立进程恢复后才通过固定验证。
全部原失败版本、原始 XML 与进一步诊断均已保留，不更换种子、不放宽容差。

这些是当前接口与 SUMO 1.28.0 的实测现象，不能据此声称所有 SUMO 场景无法保存状态。
[官方文档](https://sumo.dlr.de/docs/Simulation/SaveAndLoad.html)区分完整加载与快速加载，
并说明部分内部模型状态不保存；因此实际恢复后仍必须核验所需的闭环状态。
本环境无背景交通、自由换道或运输实体，验证不能推广到任意 SUMO 环境。

## 距离公平 DMPS 对照仍差什么

本次规划克隆真实动力学、执行器记忆和未来扰动带，具有部署控制器没有的特权信息。
不能把其结果直接与 CoopGate 比较；也不能把零 critic 的接口运行称为原论文完整复现。
下一步的小型原作者训练流程验证已有独立预定协议，正式比较还需要完整训练预算、
统一可用信息、规划模型失配处理和独立测试集。这些结论不替代性能风险保证。
