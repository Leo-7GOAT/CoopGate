# 学习控制器阻塞时的基线接管

现有`RecoveringProfile`同步调用主控制器：异常、非法指令和非有限值返回后可以回退，但主调用永久卡住时不会进入异常分支。第十七稿的加速实验降低计算耗时，没有改变这一软件接管边界。

新增的实验模块`DeadlineProfile`把主控制器放入独立进程。每个控制周期先从当时的状态与上一条实际指令计算并复核基线命令，再等待主控制器结果。消息派发和完整消息读取由独立线程承担，控制线程通过有界等待取结果。结果须匹配本次状态摘要和周期编号，并重新通过幅值、变化率和物理可恢复性检查。首次超时或错误后，本回合保持基线接管；已到达的旧结果不再使用。

该模块要求单一调用线程以及调用期间稳定的输入状态，子进程收到独立状态副本。模型加载和预热在回合前完成，子进程退出和回收放在控制回调之外；初始拒绝不创建子进程。基线自身失败会向上报告，不能以未验证命令冒充安全回退。基线准备和主结果复核耗时也计入预算；如果这两部分本身过慢，机制不能承诺满足控制周期。

## 完成的实际检查

23项测试通过，覆盖真正的子进程卡住、迟到有效结果、异常、输入修改、NaN、形状/幅值/变化率错误、物理不可认证命令、过大消息、子进程退出、启动失败、错误请求编号、基线准备及主线程复核耗尽预算。迟到结果测试让实际慢进程返回后再次调用控制器，确认后续仍使用基线。

预先提交的SUMO协议覆盖一个已完成研究的旧初态、三份固定三actor模型、四种扰动和七种分支，共84次运行。48个故障回合在第4步注入延迟2秒、永久阻塞、异常或NaN；其余为直接基线、初始拒绝和正常主控制器。学习策略在相关分支被人为设为可用，以便触发接管，这不是对置信度门控筛选能力的新实验。

全部84回合完成，没有记录到碰撞或中止。48个故障回合均在注入步开始保持基线，未发生提前回退。全部1,922次父进程完整调用均低于500 ms，最大为475.711 ms。独立复核重建84条物理轨迹、1,464条基线命令和458条实际采用的主控制器命令；12条初始拒绝轨迹与直接基线一致。60个子进程均由实际句柄完成回收，模型加载与清理成本分别保存。

内部软件预算为450 ms。本机Python使用分辨率15.625 ms的`GetTickCount64`作为`monotonic`，外层测量使用高分辨率`QueryPerformanceCounter`。24次超时触发的完整调用约为441.987—475.711 ms，不能把450 ms预算解释成严格的墙钟截止时刻。原始测量与时钟信息保留；部署整合前还需统一高分辨率计时来源并进行配对复测。不能只报告低于周期的P95而忽略最大值和启动成本。

## 与性能风险保证的关系

在精确模型、相同完整基线以及原有限扰动路径等假设下，如果一个候选原本已经通过逐车性能检查，则把某一步改为同一基线动作时，该步的基线价值差为零。因此逐步求和的确定性论证可以容纳这类拒绝；本次强制采用原始actor的故障实验本身没有满足或验证这些性能准入前提。

统计保证需要单独处理。超时决定会改变之后访问的状态、实际采用事件和退化事件，故无超时控制器的风险认证不能直接转给新控制器。即便回退动作物理可行，也不意味着相对“从初态一直运行基线”不会退化。故障后的初始准入标签和实际执行历史均保留，不能删掉失败回合或改变分母。任何后续认证都应针对固定的完整控制器、计算负载条件及真实采用定义重新设计。

SUMO在`select`返回后才推进物理时间。本次没有模拟计算等待期间车辆继续运动，也没有测量网络通信延迟。证据仅支持软件阻塞隔离、同状态基线接管及这组调用的实测时间，不支持实车计算延迟下的物理安全、总体时间分布或硬实时保证。当前正式风险校准和6,912次完整加速检查均未使用该模块。
